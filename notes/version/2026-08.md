### 2026-08-24 -- A memory address is a place you can point at, and 329 lost é's

**The three connection addresses became places.** Project leadership was right and it turned out to be
exact rather than approximate: *"its silly to say theres no solution for this … memory addresses point
to ram this means the start of the blocks are known."* Not one of strip source, strip destination or
view pointer is a free-floating address — each is a base plus an index into a grid the app already
draws, and the engine has been composing them that way all along. So the arithmetic now runs
backwards too. Every pointer field carries a plain-English line underneath (*"row 0, column 3 of
Pallet Town's border ring"*), a **⊞** opens the grid it indexes with the target square lit up so you
can click one, and the strip on the canvas grew a **✥** handle you drag in both directions. Checked
against the game's own macro for all three of Pallet Town's north pointers. An address that has left
its buffer is shown and flagged, never quietly corrected.

**POKéMON was rendering as POKMON, everywhere, and had been.** The text conversion runs through the
game's font table, which is keyed on each glyph's *name* — and for a real character like `é` the name
is the angle-bracket token while the character itself lives in the alias. So the codec could not read
those characters back in: it skipped them, and they were deleted. 329 é's and 6 ¥'s across the whole
of the map text. `¥500` had been reading as `500`. Fixed with the mirror of the adapter that was
already on the way out, and pinned by a test that walks every text entry of every map and demands
each character survive — it names all 248 losses when the fix is removed.

**Sign text ids say what the sign says.** A sign's row in the picker read literally *"a sign"* —
lowercase filler sitting among proper names like "Fisher 2". Now the list is People, then a heading,
then the Signs, each named by its own words: *"5 — PALLET TOWN / Shades of your / journey await!"*.

**"This save doesn't quite match this stage."** Picking a map state already wrote all of it; the gap
was the other direction — flip a flag by hand and the save quietly stops matching the stage it is
still reported to be in. There is now an amber offer on the Map state row that counts the
disagreements, **names them**, and waits. Nothing is written until you press the button, because a
save built between stages is a legitimate thing to hold. Two bugs the fixture caught before it
shipped: it was counting flags belonging to *other* maps, and it was raising an alarm off the state
picker's best-guess fallback rather than a real determination.

**Wander length exists, and the panel was telling you it didn't.** *"Movement needs to have an option
for wander length or something."* There is one — it was called "How far it has wandered" and filed two
groups down, while the movement blurb said in as many words that no such thing existed. Renamed to
**"Wander limit"**, and the blurb now points at it. (The limit is still bugged in the cartridge — the
game only checks one end of the range — and we still keep the bug.)

**Three labels were drawing white on white.** `palette.text` resolves to `#ffffff` on these panels, so
the Characters panel's "Room for N more" and both new pointer readouts were rendering perfectly and
invisibly. That is worse than blank, because the layout still reserves the height: it reads as a
clipped sliver of text, and two separate investigations went hunting for a layout bug that did not
exist. Written up at the top of `ui-patterns.md`.

### 2026-08-19 (4) -- Handles you can grab, and the end of the "this is live" notices

**The liveness notices are gone** — all four of them. *"Its dumb to announce messages talking about
this is live this isnt live, you scatter these in different places and its silly and takes up
space."* Three identical amber panels (warps, signs, connections) and one line in World. An editor's
edits being real is the assumption, not news. The half that carried information — whether you are
looking at the map you are standing on — stayed.

**Manual control never turns itself off.** Two things did it: it was one flag reset whenever the
selection was so much as re-touched, and the switch **disabled itself the moment the connection
desynced** — which is the moment you make your first raw edit. So turning it on and typing a number
greyed the switch out under your hand. It is per-connection state now, and only you end it.

**The manual numbers have handles.** A grip at the end of the strip drags its **length**; a grip on
the other side drags the **neighbour's width**. Each names itself and shows its value while you hold
it, and they only exist on a connection you have put on manual — so a plain strip still has exactly
one grab. ⚠️ Two delivery traps on the way, both now written down: a `Repeater` whose model is a JS
array **rebuilds its delegates** when anything in that expression changes, destroying the item
holding the drag; and a grip with its own `MouseArea` got the press and exactly **one** move, because
the pointer leaves a 14-pixel square instantly. The strip's single MouseArea decides from where the
press landed which of the three gestures this is.

⚠️ **Strip source, strip destination and the view pointer do NOT have handles yet, deliberately.**
They are addresses, and a handle for them has to mean *"which block does this land on"* — which needs
the block/bank address-space model that `map-connections.md` describes and we have not built. A
confident handle on a wrongly-derived number would be worse than a number.

**Merged tileset is a map-name preset.** Pick *"Viridian Forest"* and both pointers take that map's
tileset — the pair the cartridge ships. The tileset itself is named underneath, because the save
stores a tileset and dozens of maps share each one: the face is the handle, the caption is the truth.

**Contrast and music gained "Something else…"**, and the sign's escape was rewritten into the house
words. Contrast is a whole byte, not ten values; the music list names 151 pairs out of a possible
256×256, and now says plainly that a bank the game doesn't use makes the console run ROM as code.

**Connection strips stopped highlighting the blocks underneath them** — `hoverConnection` existed,
the cell highlight already consulted it, and *nothing ever set it*. The move anchor is placed on
whole pixels now (the strip's height is fractional at most zooms, so centring an 18-pixel disc in it
landed at 24.6 and looked low).

**Characters:** one short line instead of three, its odd width fixed (a wrapping Label in a Layout
needs its preferred width pinned), and a full indoor map now *says* it is out of room — which is what
made the indoor rule look broken when it was working correctly.

### 2026-08-19 (3) -- The board, worked down: the dead zone, the bike, the doors that go somewhere

**Connections were "almost impossible to use"** — *"they move around super glitchy and choppy,
clicking and dragging just jerks it all over the place"* — and that is a feedback loop, not a
smoothness problem. The drag measured the pointer in coordinates **local to the connection itself**,
and the connection's position IS the thing the drag changes: drag right, the offset goes up, the
strip slides right, the pointer's local x therefore goes *down*, a smaller offset is written, the
strip slides back. Every frame, both directions. It measures in the parent's fixed space now; a
90-pixel drag moves it exactly four blocks, which is what a 90-pixel drag should do.

**The edge of the world reads as a dead zone.** The border ring used to get a translucent wash laid
over the top, which says *"the same world, shaded"* — the opposite of the point. Its shades are
replaced now, with a cold flat ramp of its own, after the palette pass, so it holds whatever
contrast or colour filter is in force (a wash disappeared into the glitch palettes entirely). Still
four distinct steps, so a neighbour's edge bleeding into the ring stays readable. ⚠️ And a second
bug underneath: toggling the layer changed nothing on screen, because the map image's URL notifies
on one signal and the layer wrote a different one. Found by byte-comparing two screenshots rather
than trusting that they looked different.

**The player rides the bike** when the save says they do — the game's own artwork, which needs no
other change because the console swaps the player's graphics wholesale and keeps the same animation
table. **And constructing a map now sets that flag correctly**, which is what makes it honest: the
console only ever holds it on the Cycling Road (four exact tiles set it; both gates clear it), so
constructing Route 17 arrives on the bike and constructing Pallet Town does not. Without that, the
new sprite would have drawn Red pedalling around outside his own front door.

**Placed warps, signs and people go somewhere real.** A placed warp was `$FF` every time, a placed
sign always took the map's first placard, and a placed person arrived with "Nothing to say" — so
the maker tools produced identical furniture you then had to edit one by one. Each now draws from a
pool that is legitimate by construction: the map's own doors, its own sign texts, its own people
texts. Nothing invented, nothing validated after the fact.

**"Arriving at warp #" offers the destination's landing spots, named** — *"0 — Route 12 Gate 1F, at
(4, 0)"* instead of a 0–255 box that asked you to know how many a map you are not looking at
happens to have. The full range is still one "Something else…" away.

**Connections got their manual controls.** The neighbour picker is the shared map selector at last
(this was the last bespoke map list on the screen); the three addresses are shown and typed as
addresses (`$C6EB`, not `50923`); "Break sync" is **"Manual control"**, because "break" names the
damage rather than the capability; and the ROM's own symbols are gone from the blurbs — they named
the byte for someone who already knew and told everyone else nothing.

**Every remaining useless flag is gated, and no row says "leftover".** The decision used to be made
by searching the description for the word "reads" — so *"Nothing ever reads it back"* counted as
proof that it WAS read, and every write-only flag stayed on screen. The read/write counts the
research always had are carried into the data now. ⚠️ And the fix nearly went too far the other way:
counting only script checks would have hidden **335** real "Beat <map> Trainer n" flags, which the
engine reads from the map's trainer table and which genuinely re-arm a battle when you clear them.
Both directions are pinned.

**"Safe on this map" says which rule you are under** — indoors any character is allowed until the
video memory runs out; outdoors the map loads a fixed set and nothing else will draw. The rule was
already right; what was missing was any sign of which one applied.

### 2026-08-19 (2) -- The first person on every map was invisible

A save-fidelity bug, found from a report that sounded like a UI quirk: *"Some filter flags like Rocket
1 wont appear if toggled but Rocket 2 and 3 toggle just fine in Pokemon Tower 7f."*

Rebuilding a map's cast from the cartridge's own data **threw the player away**. `AreaSprites::setTo()`
(and `randomize()`) emptied the list and refilled it straight from the ROM, so the map's **first
object landed in slot 0** — the slot everything reserves for the player and therefore skips. After any
constructed map change the first object of **every** map was gone: not drawn, not draggable, and its
filter flag toggled something nothing could show. Rocket 1 is simply Pokémon Tower 7F's first object.

The half that matters more: saving writes the sprite count as *"everyone but the player"* and stores
slot `i` at index `i`, so the count came out one short and **the first NPC's bytes were written over
the player's own sprite record**. Both halves are fixed and pinned — the player object itself is kept
across a rebuild (not replaced), so his bytes are untouched by a map change, and
`tst_map_sprites::constructingAMap_keepsThePlayerInSlotZeroAndEveryObject` checks the count, the
slot-0 occupant, every object's coordinates and flag index, and the saved count.

**The highlight that pushed the page around.** *"When a panel is opened and entry highlighted the
highlight is actually way too tall and creates a lot of extra space above the item until the highlight
goes away which causes everything to re-flow. It looks bad."* — a QML trap: **a Layout manages every
visible child**, so the highlight rectangle, declared inside the row's column, stopped being a
backdrop the moment it appeared and became a second cell stacked above the row. Its `anchors.fill` was
ignored (anchors don't apply inside a Layout), which is why its height was arbitrary. The row is a
plain `Item` now, the highlight is anchored to the content, and it cannot move a pixel of layout.

**The wrench moved to the left of the "!", and both popups are named properly.** *"It should not show
more options as a title… that should be titled better too."* Both were named after their *size*
("more", "uncommon"), which is why they read as the same button twice. They are named after their
*subject* now: **Deeper controls** (the wrench — how deep do you want to work?) and **Values that
don't behave** (the "!" — is this value real?). Reading order runs ordinary → deeper → abnormal.

**The glitch palettes come back out of the Tinkerer gate**, to a switch of their own in the contrast
dropdown, exactly where they used to live. *"The glitch palettes aren't finicky to work with, they're
fun."* Right — Tinkerer means *real but finicky to set from a save* (a warp half-executed, a fall in
mid-air); a glitch palette is a finished, stable render with no state to get wrong. Filing it with the
mid-motion states told a lie about the console, and hid the fun thing behind a door marked
"difficult". It is written down as the one named exception, with its reason, so nothing else can cite
it as precedent.

**The map selector goes back to By tileset, and only the connection picker opens on By connections.**
The connection picker was getting its sort by **writing the shared setting**, so opening it once
re-grouped every map list in the app for the rest of the session, with nothing on screen to say why. A
list may answer its own question now (`ownSort`) without answering everyone else's.

**Harness:** the models are reachable at last — `@map`, `@file`, any Bridge model by name — and
`invoke` converts arguments to the method's real parameter types and hands the **return value** back.
Between them that turns "drive the UI until the answer appears on screen" into one call; the sprite
bug above was found and proven with three of them.

### 2026-08-18 (22) -- Manual has something behind it, and the connection picker joins the fold

The **Manual** gate now does what it was declared for. It reveals — and only reveals — the two
hand-controls for values the app keeps in sync for you:

- a connection's **Raw bytes** section, with its "Break sync" switch, and
- the **camera / view box**, with its loose/attached switch and raw address.

*"It doesn't switch them to manual, it just shows them, allowing to break auto sync."* So opening the

the switch yourself. Each keeps an escape hatch that is **not** a second gate — a connection that is

otherwise the panel would be hiding the only explanation for what the map is doing.

Three fixes in the same pass:

- **The connection picker uses the shared map selector** — sort · search · grouped rows, like every

- **Connection tooltips were dark-on-dark.** That file was the last one still using the stock

- `tst_warps` gains **`tinkererFields_areAbsentUntilThatGateIsOpen`**, which asserts both halves of the

and so they are two different buttons (leadership: *"Tinkerer, Debug and Manual should be their own

Deliberately **not** gated: "Falling drops you onto", "You fell down a hole", "Dig / Escape Rope /

### 2026-08-18 (19) -- ⭐ `<f>` was never a name token · the animation section, restored and deepened

**`JUNE<f>` finally reads `JUNE♀`, and the reason it kept failing is worth writing down.**
*"The sign still reads as JUNE`<f>` ... i just want the stupid characters to convert which seems
impossible for you to do so far."*

It was not impossible — it was **the wrong layer**, three times. `FontsDB::expandStr` is a *codec*: it
converts a string to the game's font codes and back, and `convertFromCode` returns each glyph's
**`name`**, which for a non-ASCII glyph IS the angle-bracket token. That is exactly right for
round-tripping and useless for reading. `<f>` was never a name token that name-substitution could
reach: it is **font code 245**, and `font.json` has carried its real character all along, in
**`alias`** —

| code | name | alias |
|---|---|---|
| 245 | `<f>` | ♀ |
| 239 | `<m>` | ♂ |
| 186 | `<e>` | é |
| 84 | `<poke>` | Poké |
| 117 | `<...>` | … |

So `friendlyText` gained a final pass, `fontTokensToCharacters`. ⚠️ It substitutes only glyphs that
are genuinely **characters** — `singleChar`/`multiChar`, never `control` (`<page>`, `<line>` — that is
structure), never `picture` (tilemap graphics), never `variable` (already resolved). And even among
those, some aliases are *descriptions*: `<E>` is "Bold E", because Unicode has no boxed bold letter.
Those fall out on the shape of the alias itself — a real glyph is short and has no space — which is why
"Poké" and "……" pass and "Bold E" and "Player Name" do not.

**The animation section is restored, and deeper than before.** *"You've removed important data from the
indoor/cave/outdoor ... theres only 2 bullet points and we're missing other data that was there ... you
made it way worse and watered down."* Fair, and the mistake is worth naming: the previous pass went
after **accuracy** (the Surf bullet was asking the wrong question) and, in tightening it, quietly
deleted content — the Surf line vanished entirely on a save that was not surfing. **Fixing a wrong
sentence is not a licence to delete the true ones around it.**

Six bullets now, in the order a person reads them, everything
`reference/map-animation.md` established:

1. **What animates, and how fast** — nothing / water on a **20-frame** cycle / water + flower on **21**.
2. **Water, tile `$14`** — both-ways conflict, and *how*: the game **bit-rotates the tile's own 16
   bytes** (right ×4, left ×4), it does not swap frames.
3. **The flower, tile `$03`** — both-ways conflict, and that its four frames (**1·1·2·3**) are copied
   **over** `$03`; a non-flower tile there is replaced, not animated.
4. **Surf** — stated **every time** as a fact about the setting, and escalated to a "!" only when this
   save is actually surfing and would be dropped to walking.
5. **Is this the tileset's own value** — and if not, what it was changed *from* (a dot cannot say that).
6. **A byte above 2** — not garbage: the console tests `and a` then `rrca`, so odd collapses to Cave
   and even to Outdoor. It now says **which**.

### 2026-08-18 (18) -- ⭐ "Has water" is not "meant for surfing" — the animation warnings, rebuilt on the disassembly

*"Just because a map has water doesnt mean its meant for surfing — dont use lazy approaches. Silph Co
1 has water attraction and its indoors and your not supposed to surf there."*

Correct, and the Surf bullet was built on exactly that lazy proxy (`tilesetHasWater`). Asking
`pret/pokered` settles it: **`hTileAnimations` has exactly ONE behavioural reader** in the whole game
outside the animation loop — `LoadPlayerSpriteGraphics` (`home/overworld.asm:815`):

```
ld a, [wWalkBikeSurfState]
dec a
jr z, .ridingBike        ; 1 = biking
ldh a, [hTileAnimations]
and a
jr nz, .determineGraphics
jr .startWalking         ; <- byte is 0 while SURFING: forced back to walking
```

So **"0 breaks Surf" is about the player's own movement state, not about the map being surfable.** The
warning now asks `wWalkBikeSurfState == 2` (new `MapModel::playerIsSurfing`) and the Surf line does not
appear at all on a save that is not surfing — so Silph Co's ornamental pond says nothing.

**Conflicts now cut both ways**, which is what leadership asked for: a bullet earns a mark when this
setting and the tileset *disagree*, in either direction —

- tileset HAS water, setting doesn't animate → its water sits dead still;
- tileset has NO water at `$14`, setting animates it → **something else is being warped**;
- tileset HAS a flower, setting doesn't animate → it sits still;
- tileset has NO flower at `$03`, setting is Outdoor → that graphic is **overwritten**, not animated.

**⚠️ And the "can place any character" bullet is GONE — it was wrong.** Added on leadership's word
earlier the same day, removed once the disassembly was asked; they had flagged the doubt themselves
(*"i dont know what will happen with the sprites when an indoor map is pushed outdoor … maybe figure
that out"*). **Answer: nothing happens.** Every other use of `hTileAnimations` is a save/restore around
menus and screens. Which characters may stand on a map is decided by the map's own header, never by
this byte — so a bullet claiming otherwise would have been a confident lie, and no "!" is owed either.

**The search marks were rebuilt.** *"The random and clear buttons at top are not part of the apps
theme/style/chrome we've been building — there too far apart, separate buttons, you didnt make them
right."* True: two free-standing 30 px squares beside the field made a row of four disconnected boxes
with the field shrinking to fit. Clear and Random are not separate jobs, they are things you do **to**
the search — so they now sit INSIDE its rounded edge as flat borderless marks. Clear **dims** rather
than vanishing when the box is empty, so the field doesn't twitch on the first keystroke.

**More he/him found and fixed.** The first sweep grepped for `tr("` on one line and therefore missed
every **continuation line** of a multi-line string — five in `mapmodel.cpp`, three in
`maplayersmodel.cpp`. ⚠️ It also caught a bug I had introduced: `DetailsPanel`'s `playerGroupOrder`
must match `MapModel::playerFields`' group names **exactly**, and renaming only the C++ side would have
made the whole "What they can do here" group vanish from the panel.

### 2026-08-18 (17) -- ⭐ Continuing into a cutscene: CONSOLE-ANSWERED · the player is "they"

**The question leadership wanted settled before anything was gated.** *"Dont have state steps like
Step 1, Step 2, Step 3 ... if i select this and load the game the continue feature i dont think can
enter a cutscene. Please investigate ... but i need solid confirmation first."*

New probe `scripts/emu/probe_transient_state_steps.py` writes each of Pallet Town's seven script
values, Continues into it, and asks three behavioural questions: does it come up, does it stay up, can
you walk.

| value | kind | verdict | walked |
|---|---|---|---|
| 0 `DEFAULT` | resting | **playable** | (5,6) → (5,8) |
| 1 `OAK_HEY_WAIT` | transient | **controls held** | (5,1) → (5,1) |
| 2 `OAK_WALKS_TO_PLAYER` | transient | **controls held** | (5,1) → (5,1) |
| 3 `OAK_NOT_SAFE_COME_WITH_ME` | transient | **controls held** | (5,6) → (5,6) |
| 4 `PLAYER_FOLLOWS_OAK` | transient | playable | (5,6) → (5,8) |
| 5 `DAISY` | resting | **playable** | (5,6) → (5,8) |
| 6 `NOOP` | resting | **playable** | (5,6) → (5,8) |

**All three resting values play. Three of the four transients do not.** No crash and no freeze — the
console comes up, animates, and then *keeps the controls*, because a cutscene is running and the game
is driving. Two of them also **move the player to the cutscene's staging square (5,1)** before you

### 2026-08-18 (14) -- ⚠️ The pinch was compounding on itself

*"If i position the mouse cursor over the center and zoom in or out it moves way off the edge of the
map quickly — the zoom with pinch on laptop touchpad and mouse both do this."* The earlier fix was
real but partial: it corrected the zoom **tool**. Two more faults were behind the rest of it.

- **`activeScale` is CUMULATIVE from the start of the gesture** — 1.0, 1.1, 1.2, … — and the pinch
  multiplied it into `canvasRoot.zoom`, which the *previous frame had already updated*. So every frame
  re-applied the entire gesture so far on top of itself: the zoom grew geometrically, no anchor could
  hold against it, and the map shot off screen. The classic absolute-vs-relative mix-up, and it looks
  correct on exactly the first frame. A cumulative factor now multiplies the zoom the gesture
  **started** at, captured on `onActiveChanged`.
- **And the anchor's coordinate space was being guessed at.** `zoomAround` reads `centre` as
  Flickable-local, but its three callers have three different parents: the ground `TapHandler` lives
  inside `canvas`; the wheel and pinch handlers are declared inside a `Flickable`, whose default
  property reparents *visual* children into `contentItem` — so what a handler's `position` is relative
  to is genuinely not obvious from reading the file, and getting it wrong is silent. Every anchor now
  goes through one new function, **`view.pointInView(scenePosition)`**: take the point from the SCENE,
  which every handler reports identically, and map it once, in one place. Nothing left to deduce.

### 2026-08-18 (11) -- A map state now moves the CAST too, and the keystone got stricter

The same two-writes fault reached by its **second** road. `applyState()` was writing its missable
flags with `WorldMissables::missablesSet()` directly, so applying or rolling a stage changed the flags
and left the sprite slots exactly as they were — the map's people did not follow the state they were
supposed to belong to. Now routed through `setMissableShownQuiet()`, so the cast moves with the stage.

- **A quiet variant exists for a reason.** A Silph-liberation stage moves **44** missables in one
  gesture; one `changed()` per flag would have every binding on the screen re-evaluate 44 times for a
  single apply. `applyState` emits once at the end, which is what one apply should look like.
- **⚠️ `tst_map_states::applyState_writesOnlyStateBytes` caught this immediately** — *"byte 0x2d3c
  moved — outside every state region"*, which is slot 1's picture id, Prof. Oak's. The keystone was
  doing its job, and the right response was to widen its contract **narrowly**: the two picture-id
  bytes of each of the 16 slots (`0x2D2C + 0x10·slot`, and the game's second copy at
  `0x2E2C + 0x10·slot + 0xD`) are now legal targets, and **nothing else in those slots is.**
- **The guarantee got stronger, not looser.** A stage may now change *who is standing on the map*, but
  it still may not move anyone, turn anyone, retime anyone, or edit what they say. The first
  coordinate byte a future wholesale rebuild touches — the *"sprite is reset for no reason"*
  leadership ruled out — turns this test red.

### 2026-08-18 (10) -- ⭐ Showing a missable is TWO writes · point at a thing, get the thing · the zoom tool's anchor

**The toggle bug, root-caused.** *"Some toggles still dont work like the receptionist is not there
despite toggled on, the map wasnt reconstructed well"* … *"Daisy sitting doesnt show when toggled on
Blues house map."*

Hiding an object on a real Game Boy touches **two** places, and `missable_objects.asm` does both:
`ShowObject`/`HideObject` set or clear the `wMissableObjects` bit **and** write the sprite slot's
**picture id** — `HideObject` stores **0**. And picture id 0 means *"this slot is unused"*
(`ram/wram.asm`), which is exactly what `MapModel::npcList()` skips on. We were writing the bit and
nothing else, so clearing it left behind a slot that still declared itself unused: the renderer
skipped it and the object never came back however many times you toggled it. **The switch was writing
a true byte into a save the renderer had already been told to ignore** — which is why it presented as
"the map wasn't reconstructed well" rather than as a dead switch.

- New **`MapModel::setMissableShown(missableInd, shown)`** does both halves; the World panel's
  switches and the Details panel's `FlagChip` both route through it. Calling
  `WorldMissables::missablesSet()` from the UI is now a bug.
- **The restore is deliberately minimal — the slot is NOT rebuilt from the ROM.** The console only
  ever zeroed the picture, so coordinates, facing, movement, text id and the trainer fields are still
  its own data and are exactly right; putting the picture back is the whole inverse operation.
  Rebuilding would also be the *"sprite is reset for no reason"* leadership ruled out in the same
  brief. The picture comes from the slot's own `pictureIDCopy` (spritestatedata2 field d, which
  `HideObject` does not touch), falling back to the map's ROM object list.
- The slot is found by the save's **own** link (`wMissableObjectList` at `0x287A`, which survives
  hiding), not by a positional guess.
- **Verified live, both ways:** Pallet's Prof. Oak chip HIDDEN → SHOWN draws him in full; SHOWN →
  HIDDEN removes him and leaves his box. Write-up + the one still-open case (the *constructed*-map
  path must honour the bits when it builds slots) in
  [`reference/map-scripts-missables.md`](../reference/map-scripts-missables.md).

**Point at a thing and you get the thing.** *"When mousing over connection icons the blocks underneath
highlight when its not supposed to when mousing over objects."* Two faults in one sentence: connection
arrows never announced themselves at all, **and** the white cell outline was not consulting the
announcement even for the objects that did make it — sprites, doors and signs have set `hoverMovable`
since July, but only the tab strip ever honoured it, so pointing at any of them lit both. New
`hoverConnection` + `hoverOverObject`, and the outline stands down.

**⚠️ The zoom tool was anchoring in the wrong coordinate space.** *"Fix the zoom its whacky as heck, it
should zoom where the cursor is."* `zoomAround(newZoom, centre)` reads `centre` as **Flickable**
coordinates; the zoom tool passed the ground `TapHandler`'s position, which is **canvas**-local — the
two lines above it divide by the zoom for exactly that reason. So the anchor was wrong by the whole
scroll offset, and the further you had scrolled the further the map jumped. The wheel and pinch
handlers are children of the Flickable, so theirs were always right, which is why only the tool
misbehaved.
