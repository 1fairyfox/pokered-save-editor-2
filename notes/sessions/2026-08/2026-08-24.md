## Q2 — The three connection addresses became places you can point at

Leadership pushed back on a deferral, and they were right:

> *"i am aware of how hex addresses and memory addresses work, when i asked you for move and drag
> handles and stuff, i know we're talking about memory addresses but its silly to say theres no
> solution for this. The way i saw it when i asked the question, memory addresses point to ram this
> means the start of the blocks are known, i figured handles on the visual map could be relative to
> that address somehow … Theres no reason at all the hex addresses just simply have to be that way
> because there hex addresses, and that theres no way to make it intuitive and easy."*

**They were right, and it is exact rather than approximate.** None of the three is a free-floating
address — each is a **base plus an index into a grid this app already draws**, and the engine has
been composing them that way all along (`MapEngine::viewPointer` builds one from a block coordinate;
`c.srcAddr = to->getDataPtr() + blk` builds another; `destIndex = stripDst - overworldMapAddr`
already takes a third apart).

| field | base | the grid it indexes | stride |
|---|---|---|---|
| Strip source | the neighbour's block data in ROM | the **neighbour's own map** | its width |
| Strip destination | `wOverworldMap` (`$C6E8`) | **our border ring** | our width + 6 |
| View pointer | `wOverworldMap` (`$C6E8`) | the **neighbour's ring**, after crossing | their width + 6 |

`MapModel::pointerPlace()` runs that backwards; `setPointerPlace()` runs it forwards. Verified live
against Pallet Town's north edge and the `map_connection` macro in
[map-connections.md](../../reference/map-connections.md):

```
stripSrc -> row 15, col 0   ==  W*(H-3) = 10*15 = 150   (the neighbour's last three rows)
stripDst -> row 0,  col 3   ==  _tgt = offset + 3
viewPtr  -> row 18, col 1   ==  (W+6)*H + 1 = 16*18+1 = 289
```

**Four things shipped:** the decode; a plain-English readout under every pointer field; a **⊞**
picker that opens the grid the pointer indexes with the target square lit (click to set); and an
on-canvas **✥** grip on the strip that drags in *both* axes, because a pointer into a grid is a
square and should move like one. Drag tested end to end — (row 0, col 3) → (row 9, col 15), clamped
correctly at the grid edge, ring redrawn live.

### The traps

* **Floor division, not C truncation.** `-1 / stride` truncates toward zero and would report row 0
  for an address a whole row *above* the buffer — the difference between "just off the top" and
  "fine". An out-of-grid address is shown and flagged amber, never clamped.
* **The picker draws the SAVE's ring for the loaded map**, not the ROM's. Strip destination points
  into our own border ring, so the picker's grid and the canvas behind it must be the same picture.
  A ring that is *nearly* right is worse than one that is obviously a reference.
* **`makeStateCoherent`-style scope discipline:** the on-canvas grip and the picker both write
  through `setPointerPlace`, which composes only from that grid's own base and stride, so a pointer
  edit is provably a two-byte edit (pinned).

Pinned by three tests in `tst_connections`: the macro check, the out-of-grid honesty check, and the
round-trip that also proves the two-byte write.

## Q3 — The friendly-string function, and 329 characters it was deleting

Leadership was openly wary of this one (*"you seem to totally lose your mind completely like all of
your intelligence if that function comes into focus"*), so: read first, report, then change.

**What it is.** `FontsDB::expandStr` is a **codec** — it runs a string through the game's own font
table and back. It resolves the variables (`<player>`, `<rival>`, `<poke>`, `<pkmn>`, `<pc>`, `<tm>`,
`<trainer>`, `<rocket>`, `<dex>` …) and obeys the text-box structure codes (`<page>`/`<para>`/
`<cont>`/`<end>`/`<prompt>` truncate; `<next>`/`<line>` become `\n`; the box caps at two lines).
Every part of leadership's description was correct: it translates *from* game characters into
readable computer text, it covers variables and symbols, and it is not a game text renderer.

**And it was silently eating characters.** The codec is keyed on each font entry's **`name`**. For a
glyph that is a real character — `é`, `♀`, `…`, `×` — the name is the angle-bracket *token* and the
character itself lives in **`alias`**. So `convertToCode` found no entry, skipped it, and the
character was **deleted**. Captured from the running app, Safari Zone Entrance text 4:

```
before:  "For just 500, ... the POKMON you ... special POK BALL"
after:   "For just ¥500, ... the POKéMON you ... special POKé BALL"
```

Census of the whole corpus: **é appears 329 times, ¥ 6 times**, across 738 text entries. Every one
was losing them, and it had been on screen the whole time — you simply cannot see a missing letter
unless you know the word.

**The fix** is `charactersToCodec()`, the exact mirror of the existing `fontTokensToCharacters()`, at
the same boundary as `pretTokensToCodec`. **Single-character aliases only** — the multi-character
ones are a trap: `<poke>`'s alias is `Poké` and code `0x54` expands to `POK<e>`, so a literal "Poké"
would come back case-changed. Plus one explicit pair for `¥`, whose font entry is named `$` and so is
reachable by neither half of the symmetric rule (exact: a literal `$` appears in zero of the 738
entries).

**Deliberately NOT in the codec.** `convertToCode` is what the trainer/rival name editors validate
against; teaching it to accept aliases would change which characters those accept. Same reasoning and
same boundary as `pretTokensToCodec`, which is already documented that way.

Pinned by `tst_signs::everyCharacterInEveryMapsText_survivesTheTrip`, which walks every text entry of
every map. **Negative-controlled:** with the fix removed it fails naming all 248 losses by map, id
and codepoint.

> Flagged, not changed: 41 entries contain `@`, the game's string terminator, where one entry holds
> several script-triggered messages. It is dropped silently, which welds two sentences together.
> Showing it as a paragraph break would read better, but that is a presentation decision.

## Q1 — "Indoor" meant two different things on one screen

*"In Pallett Town, the opening save file as it is, changing it to indoor keeps the list treated still
as outdoor."*

The app was right. `engine/overworld/map_sprites.asm`:

```
InitOutsideMapSprites:
    ld a, [wCurMap]
    cp FIRST_INDOOR_MAP   ; is the map a city or a route?
    ret nc                ; if not, return
```

The console decides sprite loading from the **map id alone** — the tileset is never consulted. What
leadership hit was a **naming collision**: the control labelled "Indoor / Cave / Outdoor" is
`sTileAnimations` (save `0x3522`), a verified 1:1 rename that controls what *animates*. Two unrelated
things wearing the same word, one screen apart. Fixed at both ends — a clarifying line under the
control, and the characters blurb now names the **map** ("This map is outdoors: …") rather than a
condition you might think you are setting.

## The invisible-text trap — three labels, one afternoon

`color: palette.text` resolves to **`#ffffff`** on this app's panels, and the panels are white. Three
labels were rendering perfectly and invisibly: the Characters panel's "Room for N more" and both new
pointer readouts.

What made it expensive is how it *looks*. Invisible text is not blank space — the layout still
reserves the height and antialiasing leaves a ghost, so it reads as **a clipped sliver of text**, and
the obvious diagnosis is a layout bug. Two investigations went into `Layout.preferredWidth`,
`leftMargin` and delegate stretch before anyone asked the item what colour it had ended up:

```
app_get charsRoomLine height -> 14                   # correct
app_get charsRoomLine text   -> "Room for 12 more"   # correct
app_get charsRoomLine color  -> "#ffffff"            # ← there it is
```

Swept every QML file; those were the last three. Written up at the top of
[ui-patterns.md](../../reference/ui-patterns.md): **if a label is mysteriously missing, query its
`color` before touching the layout.**

## Board #11 — "This save doesn't quite match this stage"

Picking a map state already wrote all of it (`applyState` moves the event flags, the shown/hidden
objects *and* the badges in one gesture). The gap was the **other direction**: flip a flag by hand and
the save quietly stops matching the stage it is still reported to be in.

`stateCoherence()` counts the disagreements and **names them**; `makeStateCoherent()` ends them. Live
on the fixture, and it is a genuinely useful reading rather than noise — the save *is* past Oak's Lab,
but Pallet Town's own two one-shots have not fired because the player has not walked back in yet:

```
This save doesn't quite match "The journey underway": 2 event flags differ.
  • Pallet After Getting Pokeballs   — should be on
  • Pallet After Getting Pokeballs 2 — should be on
  [ Make them match ]
```

**Three bugs the fixture caught before it shipped:**

1. **Ownership.** A stage's block lists every flag true at that point in the story, including plenty
   set by *other* maps. Counting them made Pallet Town report mismatches for flags Pallet Town never
   writes. Honouring `ev.owned` (the rule `stageMatches()` already used) took 3 → 2.
2. **Certainty.** `currentStateId()` never answers "don't know" — it falls back to the best-scoring
   stage. Raising an alarm off a guess is crying wolf on the first panel somebody opens (the
   `dungeonWarpDestMap` / fossil lesson: *legal ≠ armed*). It now only speaks on an evidence or exact
   determination.
3. `tr("%n event flag(s)", nullptr, n)` renders the literal `(s)` with no `.qm` loaded — Qt needs a
   translation to pick a plural form.

**`makeStateCoherent` deliberately does NOT call `applyState`.** That would write the whole block
including other maps' flags — more than the box counted. A button that says "1 event flag differs"
and then reaches across the world is exactly the surprise this project treats as a defect. Same
predicate, same writes, both directions.

## Board #42 — Wander length existed; the panel said it didn't

*"Movement needs to have an option for wander length or something."*

There is one. `yDisp`/`xDisp` are the distance limit — filed under "Right now" (correctly; the game
rebuilds them on load) and labelled **"How far it has wandered"**, which describes the byte rather
than what it is for. Worse, the "Where they may go" blurb said in as many words *"There is no how
far"*, sending them hunting for a control that exists two groups down. Renamed to **"Wander limit"**,
and the axis field now points at it. The cartridge's bug is still kept and still stated.

Also in #42: the sprite's text-id picker mixed people and signs into one list, with every sign
reading **"a sign"**. Now People → heading → Signs, each named by its own words.
