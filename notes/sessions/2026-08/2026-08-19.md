## The headline — a report about one NPC, a bug about every map

> *"Some filter flags like Rocket 1 wont appear if toggled but Rocket 2 and 3 toggle just fine in
> Pokemon Tower 7f."*

That reads like a data problem with one flag. It was not. `AreaSprites::setTo()` (and `randomize()`)
rebuilt the cast like this:

```cpp
reset();
sprites = SpriteData::setToAll(map->getSprites());
```

…which throws the **player** away and leaves the map's **first object in slot 0**. Every reader of
that list honours the invariant that slot 0 is the player and skips it — `npcList()` starts at
`i = 1`, `spriteRemove()` refuses `ind <= 0`, `checkMissable()` is consulted only for NPC slots — so
after any constructed map change **the first object of every map in the game was absent**: not drawn,
not draggable, and its filter flag toggling something nothing could show. Rocket 1 is simply Pokémon
Tower 7F's first object. Rockets 2 and 3, one slot further along, were fine — which is exactly the
shape of the report.

**And it was worse than a display fault.** `save()` writes `wNumSprites = size − 1` and stores slot
`i` at index `i`, so the count went out **one short** and the first NPC's bytes were written **over
the player's own sprite record**. Byte fidelity is this project's top-tier value; this was a quiet
violation of it living behind a cosmetic symptom.

The fix keeps the player *object* across a rebuild rather than making a fresh one, so a map change
cannot edit his bytes either, and clamps both paths to the 16 slots. Pinned by
`tst_map_sprites::constructingAMap_keepsThePlayerInSlotZeroAndEveryObject` (count, slot-0 occupant,
every object's coordinates and flag index, and the saved count). Live proof before and after, on the
real app: **before** — `npcList` empty, `npcRoomLeft` 12, toggling flag 64 did nothing; **after** —
Rocket 1 at (9,11) in slot 1, `npcRoomLeft` 11, every flag working.

> **The lesson, and it generalises past this file:** *an invariant that every reader assumes and only
> one writer establishes is a bug waiting for a second writer.* `load()` established "slot 0 is the
> player". `setTo()` was written later and simply didn't know.

## The harness could not ask the model anything

Finding the above took three calls — and none of them were possible when the session started.

`brg` is a **context property**, so the models hang off the Bridge: reachable from QML, invisible to
`findChild` and to the visual-tree walk the harness uses. The harness could press any button on the
screen and could not ask the model a single question, which meant investigating a data bug by driving
dropdowns with simulated taps until the answer appeared *on screen*, then reading it off a screenshot.

Three fixes, all in `debugserver.cpp`:

- **`@name` resolves a Bridge model** — `@map`, `@file`, `@mapLayers`, anything that is a Bridge
  `Q_PROPERTY` holding a `QObject*`. No allow-list; paths still step down from there. `@` cannot
  collide with an `objectName`.
- **`invoke` converts arguments to the method's real parameter types.** It used to pass everything as
  a bare `QVariant`, and Qt matches by exact type name — so `changeMapConstructed(int)` answered *"no
  invokable/signal (or arg types don't match)"* for a name spelled perfectly right, and **every
  `Q_INVOKABLE(int)` on the models was unreachable**. ⚠️ One case is special: a `QVariant` parameter is
  not a conversion *target*, and since **every QML `function foo(a, b)` declares QVariant parameters**,
  missing it meant no QML-side function was callable either.
- **`invoke` returns the result.** Queries answered `true` and discarded it, so `npcList()`,
  `storageMissables()`, `warpStateFields()` — the whole "what does the app think?" surface — stayed
  invisible even once callable.

→ [`dev-harness.md`](../../reference/dev-harness.md).

## The highlight that pushed the page around

> *"When a panel is opened and entry highlighted the highlight is actually way too tall and creates a
> lot of extra space above the item until the highlight goes away which causes everything to re-flow.
> It looks bad."*

A QML trap worth writing down: **a Layout manages every visible child.** The highlight was a
`Rectangle` declared inside the row delegate's `ColumnLayout`, written like a backdrop (`z: -1`,
`anchors.fill: parent`, negative margins) — and the moment it became visible the column adopted it as
a second **cell**, stacked above the row and adding its own height. Its anchors could not save it
either: **anchors are ignored inside a Layout**, which is why the height was arbitrary rather than the
row's. Both halves of the complaint, one cause.

The delegate root is a plain `Item` now: content anchored, highlight anchored to the *content*, Item
height = content height. The highlight bleeds 3 px past the row on purpose — as an overlay it borrows
that space instead of demanding it. → [`qt-patterns.md`](../../reference/qt-patterns.md) (top).

## The rest of the brief

**The two gate buttons, ordered and named.** *"The wrench icon needs to be left of the exclamation
icon and should not show more options as a title… actually that should be titled better too."* Both
popups had been named after their **size** — "More to work with", "Uncommon options" — which is
exactly why two buttons answering different questions read as the same button twice. They are named
after their **subject** now: **Deeper controls** (the wrench: how deep do you want to work?) and
**Values that don't behave** (the `!`: is this value real?). The wrench sits left, so the pair reads
ordinary → deeper → abnormal.

**Glitch contrast comes back out of the Tinkerer gate.** *"The glitch palettes aren't finicky to work
with, they're fun."* Correct, and the reasoning is worth keeping: Tinkerer means *real but finicky to
set from a save* — a warp half-executed, a fall in mid-air. A glitch palette is a **finished, stable
render** with no state to get wrong. Filing it with the mid-motion states told a lie about the console
and hid the fun thing behind a door marked *difficult*. It is recorded in §11b as **the one named
exception**, with the bar the next control would have to meet to claim the same.

**Map-select sorting is per-context again.** *"No it defaults to tileset for map select, the
connections default to connections sorting only here."* The connection picker had been getting its
sort by **writing the shared setting**, so opening it once re-grouped every map list in the app for
the rest of the session, with nothing on screen to say why. `MapSelectList.ownSort` lets one list
answer its own question without answering everyone else's; `mapList()` takes an optional per-call
sort.
